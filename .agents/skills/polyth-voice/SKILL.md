## Workflow and constraints
Define the desired mode: push-to-talk dictation, streaming transcription, voice conversation or TTS playback. Do not conflate an installed speech library with a working end-to-end voice mode. Map microphone permission, capture format, transport, provider/local engine, partial/final transcript, cancellation and insertion into the canonical user turn.

Inspect the current dictation package before adding a second media pipeline. Verify supported codecs, sample rates, language behavior and actual provider API/version from primary sources. Local models must be assessed on available hardware and measured latency; do not claim real-time behavior from marketing or desktop benchmarks on another machine.

Request microphone permission after user intent. Stop and release capture on cancel, navigation, disable and error. Keep interim transcript state separate from committed canonical input, and prevent duplicate final submission. An interim transcript may be shown in the draft — a draft is not a canonical turn — but only as a span the run *rewrites*, never as appended text: a cumulative update that appends duplicates re-punctuated words, and a run that ignores an outside change to the draft resurrects a just-sent message. Preserve audio privacy, retention policy, secret handling and explicit fallback choices. Do not silently upload recordings to another provider.

Test denied permission, unplugged device, silence, noisy/long speech, partial network loss, finalization races and mobile foreground recovery. Measure capture-to-first-partial and finalization separately. Read accessibility and keyboard behavior as part of composer integration. A simulated text response is not speech recognition evidence; mark provider, language and device checks that were not run.

## Current voice surfaces
- **Dictation** (`packages/dictation`): the composer mic streams a run-scoped span into the draft. Browser recognition prefers the on-device recognizer when `SpeechRecognition.available({processLocally:true})` reports it (never asked inside an Android WebView — `embeddedWebView` in `src/browser.ts`: the call there is a bad IPC that kills the renderer and the Android app, so it reports "unavailable"), applies English spoken punctuation (`applySpokenPunctuation`), stops on Escape, supports mouse/pen hold-to-talk, and is toggled by the `voice.dictate` palette command / `dictate` shortcut.
- **Dictation mode** (`VoicePrefs.dictationMode`, part of the per-person `package.dictation.voice` preference; anything but `"record"` reads as `"live"`): live streams as above. Record keeps 16 kHz PCM16 only in browser memory (`widgets/recordedDictation.ts`, capped by `DICTATION_RECORDING_LIMITS`, 10 min), turns the composer mic into a capsule carrying the take — a canvas waveform of the measured level (`widgets/recordingWave.tsx`: dB-mapped, time-keyed bars gliding toward the mic; on the phone rail cell a small centred wave above the length inside the button) and its length — and after stop creates a `mode: "batch"` session, uploads 512 KiB chunks as base64 JSON to `POST /api/dictation/sessions/:id/audio` (two in flight, a lost request resent once) and finalizes. Base64 JSON because the gateway reads a paired device's mutation body as JSON before any handler (rule `maxBodyBytes` 768 KiB, pinned by `remoteAccess.test.ts`); the route only fills batch sessions and the live hot path stays binary `/ws` frames. A failed send keeps the recording in memory: the next press resends it; Esc on the mic, a chat/project switch or switching back to live drops it. Nothing is written to disk or IndexedDB. The waveform is activity motion: under `prefers-reduced-motion`, Reduce animations (`html[data-reduce-animations]`) or Low resource mode (`body[data-desktop-low-resource]`) no canvas mounts and no frame loop runs; a still dot stands in for it, and it follows `polyth:desktop-performance-changed` live. Outside a composer rail (header placements) the canvas is hidden and its loop stops. Server side, `createDictationService({ batchAdapter })` picks the engine for recordings: the same processing policy, but a `direct-browser` live transport does not block it. `SttAdapter.transcribe()` is a provider's file endpoint — OpenAI `/v1/audio/transcriptions` with `gpt-transcribe`, Deepgram pre-recorded `/v1/listen` (raw WAV, `detect_language` for auto), ElevenLabs `/v1/speech-to-text` with `scribe_v2`, `tag_audio_events=false` and one retry without keyterms on 400/422, OpenAI-compatible the same single upload; `recordingModelFor` maps realtime-only model ids to the catalog's `recordingModel`. `transcribeRecording()` feeds engines without one (local Nemotron, Speechmatics, Wispr, extension providers) through their live stream in 100 ms writes, and failover hands the whole recording to the explicit fallback after a recoverable error. Browser Web Speech hands over no audio, so with it the mic stays live and the settings row says so. The file endpoints are checked against provider docs and stubbed-fetch tests (`recordingProviders.test.ts`), not paid live calls.
- **Capture recovery** (`widgets/audioCapture.ts`, shared by live and record mode): iOS WebKit can leave an `AudioContext` `"interrupted"` (or `"suspended"`) — the microphone indicator is lit but the worklet renders nothing. Capture resumes on start and on every `statechange` (a `resume()` that never settles is bounded), and a watchdog that sees no chunk for `CAPTURE_STALL_MS` while not paused first resumes, then rebuilds the context on the same stream, then fires `onStalled` once; the mic then shows `dictation.error.noAudio` (record mode with audio already taken sends it instead). Fake-context tests only; not yet device-verified.
- **Native capture in the iOS app**: WKWebView's getUserMedia → Web Audio path delivered no chunk at all on device (1.2.233/1.2.370 sat at 0:00 even with the recovery above) while Mobile Safari worked with the same code. So the iOS shell publishes a host primitive, `globalThis.__polythNativeAudioCapture` (`apps/mobile/src/nativeAudioCapture.ts` → `ios/App/App/PolythAudioCapturePlugin.swift`, AVAudioEngine tap → `AVAudioConverter` → 16-bit LE mono PCM chunks as base64 events; `playAndRecord` with `mixWithOthers`/`defaultToSpeaker`/`allowBluetoothA2DP`; restarts itself after interruptions and route/configuration changes; stops when the page's listeners are gone). `startPcm16Capture` uses it first (`widgets/nativeCapture.ts`, structural lookup — the package never imports the host): a refusal is `mic_denied`; any other native failure falls back to the web graph; no chunk for `NATIVE_CAPTURE_STALL_MS` fires `onStalled`. Android and browsers keep the web graph. Barge-in (`voice-mode/widgets/micMonitor.ts`) still uses getUserMedia. The app also declares `NSSpeechRecognitionUsageDescription`: without it WebKit answers Web Speech with `not-allowed`, which voice mode used to show as a blocked microphone. Voice mode now keeps the earlier route's failure when a later fallback route is refused. Fake-plugin tests only; device verification pending.
- **Read aloud and voice output**: `widgets/speechOutput.ts` is the one TTS queue — sentence chunks from `createSpeakableStream`, best browser voice via `pickVoice`, server clips prefetched one ahead with automatic fallback to the browser voice. A server voice that can stream is played while it arrives: with `stream: true`, `/api/tts/speak` answers `audio/pcm;rate=N` (headerless PCM16 little-endian mono, `TTS_PCM_TYPE`) for the services in `streamsPcm` (`src/ttsProviders.ts`) — OpenAI `response_format: "pcm"` (24 kHz), ElevenLabs `/stream?output_format=pcm_24000`, Amazon Polly `OutputFormat: "pcm"` (16 kHz, its highest) — and the whole clip for every other service and for a client that did not ask. The queue starts after 120 ms of audio, schedules later pieces back to back on the audio clock (joined to ~250 ms), plays what arrived when a stream is cut, falls back to the browser voice when nothing did, and a stopped reply closes the request so the server aborts the upstream call. Asides up to 60 characters are kept decoded per voice (16 entries), so a repeated remark is instant. Checked against the three API references (2026-11) with stubbed fetch and a fake `AudioContext` (`ttsStream.test.ts`, `speechStream.test.ts`); no paid call and no real speaker. Three read-aloud engines: browser voices, **built-in voices** (`src/localVoiceCatalog.ts` pins each Piper/Kokoro archive by size + SHA-256; `src/localTts.ts` runs them in a sherpa child process; `/api/tts/local` returns WAV) and a server voice (`/api/tts/speak`; `src/ttsCatalog.ts` lists the services — OpenAI-compatible URL, OpenAI, ElevenLabs, Google Cloud, Amazon Polly, Gradium — and `src/ttsProviders.ts` calls each at its fixed endpoint with the key typed in Settings → Voice (write-only, `data/voice-secrets.json`, per-service slot so another service never receives it) or an env-referenced key; only the OpenAI-compatible service takes a base URL, so a key never goes to a user-typed host). `/api/tts/speak` stays local-only for paired devices (a paid server); built-in voice listing/synthesis is paired-safe, install/remove is not (pinned by `remoteAccess.test.ts`, which also runs the server's policy validator). Only list a voice after synthesizing it and transcribing it back: a "text"-phoneme Piper voice and two Chinese voices fail in this runtime, Kokoro has no Japanese, and Kokoro runs slower than real time on the 4-core ARM host (≈1.2–2×), so the UI reports the measured factor.
- **Recognition routing on paired devices**: `/api/settings/voice` is not exposed to paired devices (it names endpoints and key variables). The paired-safe `/api/dictation/capability` carries the server's `selection` (provider, transport, language, policy), and both the mic and voice mode use it before falling back to local prefs — a phone must never guess the engine from its own defaults.
- **Voice mode** (`packages/voice-mode`): hands-free turns, pinned to the conversation it started in (a New chat is pinned by its first message) and running in one browser tab at a time (`widgets/tabClaim.ts`, BroadcastChannel; starting it elsewhere ends it here). The microphone stays open while the agent works; only the agent's own spoken reply closes it (talking over it interrupts) and it reopens when speech pauses for tool work. An utterance while the conversation is idle and on screen streams into the composer through `host.conversation.dictate` and is sent through `host.conversation.submitDraft` (the composer's own Send path); one while the agent works, or while another chat is open, goes straight to the pinned conversation through `host.conversation.send` with `queue` delivery — never the composer, whose sends dismiss pending permission/question requests. Spoken commands (`src/commands.ts`: stop, send now, send, cancel; configurable phrases, English + UI/recognition language defaults; only send/send now/cancel may end a longer utterance) act after a short settle instead of being sent: stop aborts the turn, "send now" alone merges the plain head of the queue into one interrupting turn (`widgets/sessionActions.ts`). `feedback: "silent"` is a control-only mode: no spoken replies, no earcons, no speaker claim. Replies (spoken/silent) is switched in the voice window itself (`RepliesSwitch` in the dock and the immersive layer), not in Settings; like every voice-mode pref it syncs as the `package.voice-mode` account preference, so the next conversation on any device starts with the last choice. A change mid-conversation (here, another tab or device) goes through `controller.applyFeedback()`: silent drops the reply being spoken and reopens the microphone, spoken reclaims the speaker and voices from the next turn. Narration while the agent works: the agent's steps are said at key moments by default (`actions` on, `narrationCadence: "key"`), its thoughts are opt-in (`thoughts`: off/brief/full). `VOICE_MODE_DEFAULTS` (`defaultsVersion` in the prefs) moves settings saved before that default once — only where narration was untouched (`thoughts: "off"`), and a later "off" sticks because the save carries the version. `src/narration.ts` turns streamed `assistant/reasoning-chunk` and `tool/call`/`tool/started`/`tool/error` into asides (localized phrases in `src/narrationPhrases.ts`, spoken in the voice's language; tool kinds come from `host.execution.describe`, with a plain tool-use fallback on older hosts). Key moments group a ~3 s window and keep ~12 s between remarks; failures are said at once; reasoning that arrives only with the final message is never read. Asides go through `SpeechOutput.enqueue(text, { kind: "aside", expiresAt })`: the reply and the user's speech drop any still waiting (`dropAsides`), only the newest one waits, one older than ~6 s is skipped, the microphone closes for them like for the reply, and talking over one silences it without dropping the turn's reply. Silent replies speak no asides, but the status line still shows the step in words (`snapshot.action`). `narrator: "model"` words grouped steps and brief thoughts with the account's small model through `POST /api/voice-mode/narrate` (`src/narrateRoutes.ts`): the client sends only a seq range of the pinned session, the server checks the session against `rc.space` (a foreign-Space id answers like a missing one) and reads the slice itself, and the model gets a digest — tool name, one scrubbed key argument, ok/failed, or reasoning text — never tool output. Only the account small model (`host.smallModel`) with `requireDirect: true` answers; none configured is `503 no-small-model` and the conversation keeps to phrases silently (never the session's own model). Limits: one call in flight and ≥4 s apart per conversation, 20/min per person across devices (`429`, the phrase is said instead), a 60 s cache per slice, 6 s model timeout. Two failures in a row keep the rest of the conversation to phrases with one on-screen notice; failed steps and full thoughts never wait for the model; a remark is never written to history. `GET /api/voice-mode/narration` (`{ configured, label }`) feeds Settings, whose "Set up" opens Settings → Sessions → Small model (`sessions.small-model`). Both routes are open to paired phones with `dictation.use` (`VOICE_MODE_REMOTE_ACCESS`); the rest of `/api/voice-mode` stays default-deny. `parseVoiceModePrefs` carries keys it does not know, so an older client's save keeps a newer client's settings. Recognition failures fall back across routes, then retry with backoff (a denied microphone waits for a tap or the page becoming visible); a refused send is a notice, never the end of the conversation. Its layer is hosted in `session.composer.before` and, as a lower-priority fallback, `composer.pending` — New chat has no area above the composer, and a running conversation must never be invisible. Every screen opens the compact dock above the composer by default (`presentation: "compact"`; full screen is an explicit preference or the dock's expand button for one conversation; a stored retired `"auto"` reads as compact). The immersive layer covers the chat column, not the whole shell: `VoiceModeHost` measures the `.workspace` box inside `.app-shell` and publishes it as `--voice-layer-block/inline-start/end` insets, plus the column's viewport top as `--voice-layer-viewport-top` (its head pads `max(space-3, --safe-top − that)`, so on phones, where the column starts under the floating header at the physical top, it clears the status bar and Dynamic Island), so the left navigator and the right rail stay visible beside it (and stay reachable — the layer is not modal and does not trap Tab). Only outside a shell does it fall back to a fixed full-viewport box.
- **Voice mode responsiveness** (same package; each item has a unit test with fakes — none of it is measured on a live provider or verified on a device):
  - *Pause that ends a turn* (`src/endpoint.ts`): `PAUSE_PROFILES` per pause preference — after a finished sentence 350/550/1100 ms (quick/normal/patient), after a question 320/450/1000, the configured `PAUSE_MS` when the words have no ending, longer (1000/1500/2300) after a trailing connective, comma or ellipsis. It reads the recognizer's punctuation only: a route without punctuation (most browser recognition) keeps the configured pause. Trailing words are per language; an unknown language ("auto") goes by the word's script and reads Latin as English, because across all Latin languages most short words are someone's connective. The streaming listener applies it through `vad.setHangover` on every partial, the browser listener when it arms its endpoint.
  - *Acknowledgement* (`acknowledge`, on by default): 300 ms after `turn/started` for an utterance sent at most 8 s earlier — never for a queued one and never before the turn has started — an aside from `narrationPhrases().acknowledgements` (`|`-separated, said in turn) unless the reply has begun.
  - *Latency* (`src/latency.ts`): marks at end of turn (with the silence waited), final transcript, `turn/started`, first speakable reply text and first reply sound. Only a turn with every mark in order is recorded; queued turns, commands and refused sends are not. The last 20 are kept in `localStorage` (`polyth.voice-mode.latency`, times only) and shown in Settings → Voice mode → Response time.
  - *Spoken-reply hint for the agent* (`src/liveRoutes.ts`): while replies are spoken the browser holds a lease through `POST /api/voice-mode/live` (`{ sessionId | null, live }`, 90 s, renewed every 30 s, dropped on silent and at the end). The package's `TURN_CONTEXT` contributor then adds `<polyth-voice>` (`VOICE_TURN_BLOCK`: answer first in one or two spoken sentences, tables/code after it) to that person's turns in that conversation — persisted with the admitted message like every turn-context block. A New chat's lease (`sessionId: null`) attaches once, to a conversation created at most 2 minutes ago. Scope first: a foreign or missing session is the same 404 and holds nothing; at most 8 leases per person. Open to paired phones with `dictation.use`.
  - *First reply chunk* (`createSpeakableStream({ firstClauseChars })`, `FIRST_CLAUSE_CHARS` 64): an opening sentence still streaming at that length starts at its last clause boundary, never inside a number, code span or link.
  - *Microphone that stays open* (`widgets/sharedCapture.ts`): where barge-in is enabled (`bargeInEnabled`) streaming recognizers (server and direct routes, through `captureFactory`) share one echo-cancelled `startPcm16Capture` for the whole conversation. A recognizer gets everything from the moment it was asked for, plus 700 ms of pre-roll after a spoken barge-in, so the words that interrupted the reply are not lost; the barge-in watcher reads the same stream; a recognizer that starts mid-speech is given the room's noise floor (quiet tenth of the last 3 s) because it cannot calibrate on speech. While the agent speaks no recognizer is attached and the audio stays in a 3 s in-memory ring. Mute, another microphone owner, a speaker claim and the end close it. The browser recognizer captures by itself and keeps the separate `micMonitor`. Apple mobile is unchanged (automatic barge-in is off there, so each turn still opens its own microphone): the native iOS audio session (`AVAudioSession` play-and-record with the speaker route) that would lift this is not implemented.
- Packages are separate bundles: microphone and speaker ownership is coordinated only through the `MICROPHONE_CLAIM_EVENT` / `SPEECH_CLAIM_EVENT` window events, and voice mode imports dictation code only via `@polyth/dictation` (browser) and `@polyth/dictation/voice-runtime`.
